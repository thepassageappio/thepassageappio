Scoped to PR #53 (`bot/vendor-partner-thin-slice` → `greenfield/passage-zero`, open, not yet merged at time of writing) — the vendor/partner persona: schema, RLS, RPCs, `/partner` queue, and `/partner/requests/[id]`. `[skip deploy]` — docs only, no code/schema change.

## Scope and approach

Per the owner's request, this pass deliberately did **not** repeat the builder's own happy-path walkthrough. It focused on adversarial and edge-case coverage the builder is less likely to hit themselves: wrong-vendor access attempts, malformed/out-of-order request states, RLS boundary checks, and mobile rendering — plus a look at the director-side origination flow, which landed as part of the same PR.

- **Preview tested**: `https://thepassageappio-h7f2884yl-thepassageappio-7018s-projects.vercel.app` (`/partner`, `/partner/requests/[id]`), confirmed matching PR #53's head commit (`bot/vendor-partner-thin-slice` @ `b2c72673326ffa43f36d0160f7cb6196c7e7d41e`).
- **RLS/RPC adversarial checks** were run as direct SQL against the isolated QA project (`passage-cycle-7a-test`, `uyacxqtsiwlvtmhxvoxr` — never production), using `set local role authenticated; set local request.jwt.claims = '{"sub": "..."}'` to impersonate specific users inside rollback-only transactions. This is the same pattern the PR's own author used for their RLS test suite, applied here independently and adversarially rather than re-running their tests.
- **One new QA test fixture was created** (isolated project only, persists — not rolled back): a second, unrelated partner organization ("QA Rogue Vendor Co (test fixture)", `partner_organizations.id = aaaa0002-...`) with one member/login (`qaaudit-rogue-vendor@passage.test`), used to attempt cross-tenant access against the real seeded Cascade Floral request. This mirrors the existing seeded-account pattern (`cycle7a-director@passage.test`, `vendor-cascade@passage.test`) and is safe to leave as a reusable fixture or delete — it touches nothing outside the isolated test project.
- The seeded fixture request (`c9a00004...`, "Arrange the viewing floral piece") was being driven through its full lifecycle concurrently by the builder's own parallel walkthrough during this sweep. Rather than colliding with that, I used it as **live positive evidence** (verified via direct DB queries of the resulting rows and event log) and ran all adversarial writes as rollback-only transactions against the same fixture without disturbing their progress.

## Findings, ranked by severity

### Medium — vendor request category is not validated against the vendor's own specialty, anywhere in the stack

`partner_organizations.category` (e.g. `florist`) and `partner_requests.category` are two independent free values. Nothing — not the director's "Send a request to a vendor" form (`PartnerRequestForms.tsx`, a plain `<select>` with all 5 categories always available regardless of which vendor is chosen), not the server action (`partner-actions.ts`, which only checks the category is *some* valid enum value), not the `create_partner_request_idempotent` RPC, and not the vendor's own `respond_to_partner_request_idempotent` RPC — cross-checks the chosen category against the target vendor organization's actual specialty.

Reproduced live: while this sweep was running, a second real request was created via the director-origination flow — "Reserve the family car for the service" (a transport job) — and saved with `category = 'florist'`, sent to and accepted by Cascade Floral & Keepsakes (a florist-only vendor, `partner_organizations.category = 'florist'`). The schema does have a distinct `transport` category available (`partner_requests_category_check` allows `florist | catering | transport | memorial_products | other`), so this wasn't a missing-option problem — it was simply never enforced. The vendor-picker dropdown also doesn't display each vendor's category, so a director has no on-screen cue to catch the mismatch either.

With only one seeded vendor this is currently invisible in practice, but as soon as a real multi-vendor roster exists, this allows (and on this evidence, already produces) requests silently routed to a vendor outside their actual specialty with no validation error at any layer.

Reproduction: as director, open "Send a request to a vendor," pick any vendor, pick any category unrelated to that vendor's specialty, submit — it saves without complaint. Confirmed via direct query of `public.partner_requests` and `public.partner_organizations` in the isolated project.

## Confirmed working correctly (adversarial, real evidence)

- **Cross-tenant read isolation (RLS) — no leak.** Impersonating a brand-new, unrelated vendor user (member of a fresh, unrelated `partner_organizations` row) via `SET LOCAL ROLE authenticated` + JWT claims: direct `SELECT` against Cascade Floral's request, Cascade's `partner_organizations` row, and Cascade's `partner_members` roster all correctly returned **0 rows**. The same impersonated user correctly *could* see their own organization's row — confirming the RLS predicate (`is_active_partner_member_for` / `can_view_partner_request`) is scoped correctly, not just failing open or closed universally.
- **Cross-tenant write isolation (RPC) — no leak.** The same rogue vendor calling `respond_to_partner_request_idempotent` and `submit_partner_request_proof_idempotent` directly against Cascade's request (bypassing the UI entirely) was denied both times with an explicit `42501 Vendor authority for this request is required` — the authorization check runs before any state/version check, so there's no way to smuggle a write through by guessing IDs.
- **Vendor cannot self-verify.** The actual assigned vendor (Cascade), calling `verify_partner_request_idempotent` on their own request, was correctly denied (`42501 Director authority for this case is required`) — verification is gated to the funeral home's own directors, not the vendor who did the work, matching the intended checks-and-balances design.
- **Idempotent replay is safe.** Re-calling `respond_to_partner_request_idempotent` with the exact idempotency key already used for a real accept returned `replayed: true` with the original result, and did not reprocess, re-charge, or duplicate an event. No double-submit risk from retried network requests.
- **Malformed/out-of-order state transitions are all rejected cleanly.** Against an already-`verified` request: a new-key accept/decline attempt, a new-key proof submission, and a new-key re-verify were each rejected with a clear, specific `55000` error ("This request is no longer waiting for a response" / "Only in-progress work can receive proof" / "No proof is waiting for review"). No state corruption, no silent no-ops.
- **Input validation holds.** An invalid `decision` value (anything other than `accept`/`decline`) was rejected with `22023` before touching any row.
- **Full happy-path lifecycle confirmed via direct DB evidence.** `sent → in_progress → proof_submitted → verified` on the seeded request, each transition backed by an immutable, correctly-attributed `partner_request_events` row (actor, previous/next state, idempotency key, version) — real audit trail, not just a status flag flip.
- **Director-origination flow works end to end.** A director-created vendor request (`create_partner_request_idempotent`) appeared correctly in the vendor's `/partner` queue and was accepted by the vendor, confirming the newer director-side half of PR #53 is wired up correctly (aside from the category gap noted above).

## Observation — not a product bug, an environment caveat worth knowing

Mid-sweep, one browser tab that had been showing a correctly-authenticated vendor session suddenly rendered "Vendor access remains closed / This account does not have an active vendor membership." Investigated before treating it as a finding: decoding the session cookie's JWT showed the active session had been silently switched to `cycle7a-director@passage.test` — a director account, not a vendor at all. That account has no vendor membership, so the "closed" screen is actually **correct behavior** for whoever that session belongs to.

Root cause: this preview's auth cookie is domain-wide, not tab-scoped, and the builder's own parallel walkthrough was signed into the same shared browser to do their director-side verification step at the same time — which overwrote the session my vendor tab depended on. Re-authenticating as the vendor immediately restored the correct queue view. Flagging only so a future concurrent-QA session doesn't misdiagnose the same symptom as a `PartnerBoundary` bug — it isn't one here, but it's worth testing directly (fresh incognito-equivalent session, not just a new tab) if it turns up again without an obvious explanation.

## What this sweep did not cover

- **True mobile-width rendering.** The browser sandbox available to me capped at 640×480 regardless of `resize_window` requests down to 390×844 — I could not get an actual iPhone-width render. At the available 640px width, both `/partner` and `/partner/requests/[id]` showed no horizontal overflow (checked programmatically via `scrollWidth` vs `clientWidth`, not just eyeballed) and looked clean in screenshots, but this is not a substitute for a real ~375–390px check. Recommend a follow-up pass with a tool that can actually shrink below 640px.
- **Decline path adversarial edges** (e.g., decline with an empty note, decline-then-immediate-resend) — code-reviewed only (the RPC does enforce a non-empty, ≤500-char note on decline), not independently provoked live.
- **Optimistic-lock (stale version) conflict** — confirmed by code review that a version mismatch raises `40001`, but not independently provoked live in this pass (would require racing two concurrent responses on the same request).
- A **second live browser session** genuinely isolated from the builder's (would need a real separate browser profile/incognito context, not just a new tab in the same shared browser) — the cross-tenant checks that matter most (RLS + RPC authorization) were instead verified more rigorously at the SQL layer directly, which doesn't depend on browser session isolation at all.
