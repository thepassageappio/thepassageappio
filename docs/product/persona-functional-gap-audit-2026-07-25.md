## Headline finding

Vendor/partner is not a small gap next to the other four — it is entirely absent from both the shipped code and the roadmap's own scoring, despite being one of the five personas the owner explicitly named. Recommend the next Passage Zero PM pass add a scored "Vendor / partner path" row to the roadmap's readiness table (parallel to the existing Funeral-home and Family/D2C rows) and sequence it into a lane, consistent with the existing critical-path note that "Demo isolation, D2C account/grant foundations, and QA automation can advance as soon as the shared identity/event contracts are fixed" — the same should hold for a minimal partner-request/quote/proof loop once Lane A's authority predicates stabilize.

Secondary finding: the director and family case-detail surfaces (`/director/cases/[id]/*`, `/case/[id]/*`) are the load-bearing gap behind the roadmap's own M3 Case Room being FAIL/PARTIAL — this audit didn't uncover a new problem there, it corroborates the existing one with a direct route-tree check.

## Session constraints (why this is an audit, not a patch)

This session has no working shell (`Workspace unavailable — the isolated Linux environment failed to start`) and no local `npm run build`/`tsc`/lint. Per this repo's own hosted-QA note in AGENTS.md, Vercel Preview deployments for this project sit behind an account/team SSO wall that blocks unauthenticated browser QA tools — the same infrastructure gap already recorded against PR #30. Scaffolding a new persona surface (new routes, components, server actions, and whatever data/RLS shape a partner-request loop needs) with no way to verify it compiles or renders would be exactly the kind of unverified shipping this repo's governance docs describe fixing after past incidents. So this pass stops at a verified, evidence-backed gap audit rather than pushing unverified code. A session with working shell access (or Vercel-remote-build verification via a throwaway branch, per the AGENTS.md exception) is the right next step to actually implement the smallest end-to-end vendor slice (e.g. `/partner` list view + `/partner/requests/[id]/quote` accept/decline, mirroring the existing `/staff` slice's pattern of a real server action wired to hosted data).

## Additional finding this session: `check-release-train.js` / PR template mismatch

Independent of the persona audit above: pushing a commit onto `bot/cycle-8-task-proof-loop` (PR #30's head branch) triggered the `Passage candidate validation` workflow, and its `check-release-train.js` step fails for PR #30 (and would fail identically for PR #24). Root cause: the script hard-requires a `## Founder Review` section with `Founder Reviewer:` and `Founder Review: APPROVED` fields, but PR #24, #30, and #34 were all written against an older template that uses `## Development Head / Release Authority` instead — that heading never existed in this script's required list. This is a genuine template/schema drift, not noise from unrelated in-progress work. Unlike the already-fixed main-branch author-gate bug (a mechanical identity check the owner already deprioritized), this script enforces a substantive founder-approval requirement, so reconciling it is an owner decision, not an agent one — it should not be loosened without the owner explicitly deciding whether the intent is "require real founder sign-off" (fix the PRs/template) or "the Development Head role already satisfies this" (fix the script). Left unmodified this session pending that decision.
