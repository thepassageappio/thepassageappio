# Passage Authority — QA, Persona, and UI/UX Report
**Date:** September 9, 2026
**Scope:** Live production (`www.thepassageapp.io`, Vercel `passage-authority-uat`, Supabase "Passage Authority UAT" + "passage-demo")
**Method:** Fresh, independent verification only. No prior QA report (including the September 7 report) was taken on trust — every claim below was re-checked today against the live site, live databases, and live HubSpot account, with a brand-new synthetic test organization.

---

## Verdict

**Not demo-ready.** A newly signed-up institution owner — the exact persona a bank or credit union buyer would be — cannot get past mandatory two-factor setup and is permanently locked out of the product. This is a full-stop blocker discovered during real QA, not a hypothetical: it happened on the first live signup attempt and reproduced on every retry. Until it's fixed, no new prospect can self-serve the free evaluation, and I could not test the institution-review workflow or role scoping through the UI as a result.

Separately, the database's own schema advisor reports that 20 tables holding commercial/billing and participant-session data have Row Level Security disabled — a finding that needs an engineering-verified answer (not an assumption) before any real customer data touches these projects.

On the positive side: the two specific bugs flagged September 7 (the stuck HubSpot outbox row and the two unresolved Stripe events) are genuinely fixed, re-verified today with fresh queries against both live databases. The daily reconciliation job, run fresh by me today rather than read from a log, returned **clean** on both UAT and Demo — the first real "Day 1" of the seven-day clean streak the roadmap requires. The marketing site, pricing page, and security page are well-written, honest about what's not yet certified, and visually closer to the "Apple-level minimalism" bar than most B2B SaaS sites. The signup and onboarding *forms themselves* also have two smaller markup bugs worth fixing alongside the MFA blocker.

## 2. Critical finding: new owner accounts cannot complete required MFA enrollment (P0)

**This is the headline result of this QA pass.**

Passage requires every Owner/Admin account to enroll an authenticator app (TOTP) before reaching `/app` — confirmed correct as a security requirement, and consistent with the team's own September 8 checkpoint note. But for a brand-new account created today, the enrollment screen never works:

- After completing all three onboarding steps, the app correctly redirected to `/mfa` with the message "Set up two-factor authentication" and "Preparing your authenticator setup…"
- No QR code, no manual-entry secret, and no error ever appeared — not after 15+ seconds, not after five separate reloads, not after navigating away and back.
- Direct inspection of the page found **zero** `<canvas>` or `<svg>` elements (there is nowhere for a QR code to even render) and **zero** network requests to the Supabase Auth API the whole time — the client never even attempts to call the enrollment endpoint. There were no console errors either; it fails silently.
- I confirmed this against the database directly: `auth.mfa_factors` has **zero rows** for this user. The backend has no record of an enrollment ever starting.
- The organization itself is fully and correctly provisioned server-side — `onboarding_status = 'ready'`, `status = 'active'` — so this is purely a broken client screen blocking an otherwise-valid account.
- Because the app force-redirects any authenticated, unenrolled session back to `/mfa`, this account is now completely and permanently stuck outside `/app`. I could not test team invitations, the request workflow, or role scoping as this owner for that reason — every path leads back to the broken MFA screen.

I was not able to test a second, fully isolated browser profile to double the sample size (the available browser tool shares one cookie session across tabs), so I can't rule out that this is somehow account- or timing-specific. But the evidence — a fully provisioned account, zero backend enrollment attempt, zero client errors, reproduced across five reloads — points to a real, generally-reproducible client bug, not bad luck. **This should be engineering's first priority before any outbound demo or sales motion**, since it blocks the exact self-serve "Start free" path the pricing page promotes.

## 3. Security finding: RLS disabled on 20 tables in `authority_private` (needs engineering confirmation)

Querying the live UAT database's schema directly (not a guess — read straight from Postgres' own catalog) shows Row Level Security is **disabled** on 20 tables in the `authority_private` schema, including:

- `participant_sessions`, `participant_invitation_secrets`, `organization_invitation_secrets` — session and invitation-secret material
- `commercial_accounts`, `commercial_orders`, `commercial_subscriptions`, `commercial_contracts` — billing/revenue data
- `provider_event_inbox`, `integration_outbox`, `notification_outbox` — Stripe/HubSpot event data
- `sample_access_leads`, `commercial_inquiries` — prospect contact data

The database's own advisory tooling flags this as **critical**, on the grounds that RLS is normally the only thing standing between the public/anon API key (which is not a secret — it ships in every browser bundle) and full read/write access to a table.

Important nuance, found when I tried to verify this live: Supabase's standard security-lint report (`get_advisors`) does **not** flag any of these 20 tables — it only flags two unrelated tables for a much milder issue. That gap most likely means the `authority_private` schema is deliberately *not* exposed through the public REST API (several of the table comments literally say "Server-only" / "Non-exposed"), which would make this a defense-in-depth gap rather than a live hole. I attempted to confirm this directly — trying to query one of these tables with the real anon key, the same way a browser would — and that specific action was blocked by a safety control in my own tooling before I could get a result either way.

**I could not conclusively determine whether these tables are reachable from the public internet today.** Given the tables involved (session tokens, invitation secrets, billing records), this needs a direct, deliberate check by someone with full access — either confirm `authority_private` is excluded from the exposed schema list in Supabase's API settings, or enable RLS with real policies. I'm flagging this as high-priority-to-verify rather than "confirmed breach," because that's what the evidence actually supports — no more, no less.

## 6. Functional QA — marketing site, signup, onboarding

The public marketing site (home, pricing, security) loaded cleanly with no console errors beyond harmless unused-preload warnings, and no broken links found on the pages exercised.

The `/start` → email confirmation → 3-step onboarding flow works end-to-end (aside from the MFA screen it terminates in) and is well-designed. Two smaller bugs found in the form markup along the way:

- **Organization-profile step:** two separate consent statements ("I am authorized to evaluate…" and "I will only invite people…") are rendered as one nested block with only a single actual `<input type=checkbox>` behind them. The DOM literally nests the second sentence *inside* the first checkbox's label. It's clickable and functionally gates submission correctly, but it's visually presented as two distinct attestations while only one is a real, separately-recorded consent — worth fixing given this is a compliance-attestation surface.
- **Evaluation-agreement step (step 2):** same pattern, but here there genuinely are three separate checkboxes in the DOM (`termsAccepted`, `privacyAcknowledged`, `dataUseAttested`) — the bug is that the accessibility tree only exposes two of the three as distinct interactive elements, meaning a screen-reader or keyboard-only user may not discover the third one exists as its own control.

**Confirm-email link uses a raw `supabase.co` URL**, not a `thepassageapp.io` domain: `https://ywlrxdjibngroycwnujg.supabase.co/auth/v1/verify?...`. For a security-conscious bank/credit-union buyer, a "click this link" email pointing at a third-party infrastructure subdomain rather than the product's own domain is exactly the kind of thing that reads as phishing-adjacent and undermines trust. Worth wrapping in a branded redirect.

## 7. UI/UX audit

**Desktop (1280px), homepage and pricing:** genuinely good. Restrained palette (cream background, dark green accent, one serif display face for headlines), generous whitespace, no dense SaaS-dashboard clutter, honest and specific copy ("Passage does not verify identity, approve the power of attorney, grant account access, or move money" stated right on the homepage). This clears the "Apple-level minimalism" bar better than most competitors in this space.

**Mobile (375px), homepage and pricing:** typography and layout hold up well and remain readable. One real polish issue: the primary nav row (Product / Integrations / Security / Pricing / Blog / About) overflows its container and clips "About" right at the screen edge with no visible scroll affordance (no fade, no arrow) — a first-time mobile visitor has no signal that swiping reveals the rest of the menu. I confirmed this doesn't break the page itself (the page's own scroll width is fine, 375=375), it's isolated to that one row, but it's the kind of rough edge that stands out on an otherwise very clean layout, and it's worth double-checking against the mobile-nav fix already shipped for the *authenticated* app on September 8 — this is the *public marketing* nav, a separate component.

**Security page copy** is a genuine strength: it plainly separates "what the email link does" from "what it does not do," lists a real, dated punch-list of what's still in progress before a production pilot (identity review, encryption/key-management review, pen test, etc.), and explicitly states Passage "does not claim a completed certification, independent audit, or identity integration until it can be supported with evidence." That's the right posture for this buyer and worth preserving as the product matures.

## 9. Priority list

1. **Fix MFA enrollment for new accounts** — currently a hard product-wide blocker for any new signup. Highest priority; nothing else in the product matters if no one can get in.
2. **Get a definitive answer on `authority_private` RLS exposure** — either confirm the schema is excluded from the public API (and document why table-level RLS is still worth enabling as defense-in-depth) or lock it down for real. Don't leave this as an open question with billing and session-secret tables in play.
3. Fix the HubSpot sample-access-lead upsert matching key so it stops overwriting unrelated contacts.
4. Re-point the email confirmation link at a branded `thepassageapp.io` domain instead of raw `supabase.co`.
5. Fix the nested-checkbox markup on the organization-profile and evaluation-agreement onboarding steps.
6. Add a scroll affordance (or wrap) to the public marketing nav at mobile widths.
7. Once #1 is fixed, re-run the full persona and workflow pass this report couldn't complete.
